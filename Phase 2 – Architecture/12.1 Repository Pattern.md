## 1. Repository is not a "database wrapper"

A common misconception is that `Repository = class with CRUD methods` Example of a weak design:

```csharp
public interface IRepository<T>
{
    Task<T> Get(int id);
    Task Add(T entity);
    Task Delete(T entity);
}
```

This is just another name for `DbSet<T>`.

A **real repository represents a domain boundary**.

Example:

```csharp
public interface IOrderRepository
{
    Task<Order?> GetOpenOrderForCustomer(CustomerId customerId);

    Task<IReadOnlyList<Order>> GetOrdersReadyForShipping();

    Task Save(Order order);
}
```

The consumer thinks in terms of **business concepts**, not database operations.

## 2. Repository and Aggregate Roots (DDD)

In Domain-Driven Design, repositories usually exist only for **Aggregate Roots**.

Example:

```
Order (Aggregate Root)
 |
 |-- OrderItem
 |-- ShippingAddress
 |-- Payment
```

You normally do not create:

```
OrderRepository
OrderItemRepository
PaymentRepository
AddressRepository
```

Instead:

```
OrderRepository
       |
       v
      Order
       |
       +-- OrderItems
       +-- Payment
       +-- Address
```

Why?

Because the aggregate is the consistency boundary.

You load and save the whole business object.

Example:

```csharp
var order = await orderRepository.Get(orderId);

order.AddItem(product, quantity);

await orderRepository.Save(order);
```

The repository protects the aggregate lifecycle.

## 3. Repository vs Query Service

A common advanced pattern is separating writes and reads.

### Repository

Used for domain operations:

```
Command side:

Create Order
Update Customer
Cancel Subscription
```

Example:

```csharp
await orderRepository.Save(order);
```

### Query Service

Used for read models:

```
Query side:

Get dashboard
Search orders
Generate reports
```

Example:

```csharp
var result = await orderQueries.GetCustomerOrders(customerId);
```

Because reads often need optimized SQL:

```sql
SELECT
    CustomerName,
    COUNT(OrderId),
    SUM(Total)
FROM Orders
GROUP BY CustomerName
```

You don't want your domain repository handling reporting queries.

## 4. Repository and Specification Pattern

A problem appears when repositories grow:

```csharp
GetActiveCustomersWithOrdersFromLastYear()
GetActiveCustomersWithOrdersFromLastMonth()
GetActiveCustomersWithOrdersFromPoland()
```

Soon you have hundreds of methods.

Solution:

**Specification Pattern**

Instead of:

```csharp
repository.GetActiveCustomers();
```

you define a rule:

```csharp
public class ActiveCustomerSpecification : Specification<Customer>
{
    public override Expression<Func<Customer,bool>> Criteria => c => c.IsActive;
}
```

Repository:

```csharp
var customers = await repository.ListAsync(new ActiveCustomerSpecification());
```

Now queries become composable.

## 5. Repository and IQueryable danger

A controversial topic. Some repositories expose:

```csharp
IQueryable<Product> Products {get;}
```

Example:

```csharp
repository.Products
    .Where(x => x.Price > 100)
    .Include(x => x.Category)
```

The problem:

The abstraction leaks.

Now your application knows:

- EF Core exists
- LINQ provider exists
- database translation exists

Your repository became:

```
Fake abstraction
 |
EF Core
```

You did not really hide anything.

Better:

```csharp
Task<List<Product>> GetExpensiveProducts();
```

The repository controls the query.

## 6. Repository and transactions

Example:

```csharp
var order = await orderRepository.Get(id);

order.Pay();

await orderRepository.Save(order);
```

What happens internally?

```
DbContext

Change Tracker
 |
SaveChanges()
 |
Transaction
 |
Database
```

EF Core automatically creates a transaction for `SaveChanges()`.

For multiple repositories:

```csharp
customerRepository.Update(customer);

orderRepository.Update(order);

await unitOfWork.Commit();
```

You need a shared transaction boundary.

## 7. Repository + Unit of Work

Classic architecture:

```
Application Service
      |
Unit Of Work
      |
      +-------------+
      |             |
      v             v
 CustomerRepo   OrderRepo
      |
 Database
```

Example:

```csharp
public interface IUnitOfWork
{
    IOrderRepository Orders {get;}
    ICustomerRepository Customers {get;}

    Task CommitAsync();
}
```

Usage:

```csharp
await unitOfWork.Orders.Add(order);

await unitOfWork.Customers.Update(customer);

await unitOfWork.CommitAsync();
```

However, with EF Core:

```
DbContext = Unit Of Work
DbSet = Repository
```

So adding another abstraction may be unnecessary.

## 8. Repository lifetime in Dependency Injection

Usually:

```csharp
services.AddScoped<IOrderRepository, OrderRepository>();
```

Why Scoped? Because:

```
HTTP Request
 |
Scoped DbContext
 |
Repository
```

The repository shares the same DbContext.

Example:

```
Request starts
Create DbContext
Create Repository
Execute queries
SaveChanges
Dispose DbContext
```

Avoid:

```csharp
AddSingleton<IRepository, Repository>()
```

Because:

- DbContext is not thread safe
- Memory growth
- Stale tracking data
- Concurrency bugs

## 9. Repository and Microservices

In microservices, repositories are usually **inside each service**. Example:

```
Order Service

API
 |
Application Layer
 |
OrderRepository
 |
Order Database

Customer Service

API
 |
Application Layer
 |
CustomerRepository
 |
Customer Database
```

Never:

```
Order Service
 |
CustomerRepository
 |
Customer Database
```

because services own their data.

# 10. Repository and Outbox Pattern

Very common combination.

Example:

Create order:

```csharp
public async Task CreateOrder(Order order)
{
    await repository.Add(order);

    await outbox.Add(
        new OrderCreatedEvent(order.Id));

    await unitOfWork.Commit();
}
```

Database transaction:

```
BEGIN TRANSACTION

Insert Order

Insert Outbox Message

COMMIT
```

Background worker:

```
Outbox Table
      |
      |
      v
Message Broker
      |
      |
RabbitMQ / Azure Service Bus
```

This prevents:

```
Order saved
     |
     X
Message publishing failed
```

# 11. Repository and Testing Strategy

Bad test:

```
Service
 |
Repository
 |
EF Core InMemory Database
```

This tests EF behavior, not your business logic.

Better:

```
Service
 |
Mock IRepository
 |
Fake data
```

Example:

```csharp
var repository =
    Substitute.For<IOrderRepository>();

repository.Get(id)
    .Returns(order);
```

Your service test becomes fast and focused.

# 12. Modern recommendation matrix

| Application         | Recommended approach                              |
| ------------------- | ------------------------------------------------- |
| Small CRUD API      | Direct DbContext                                  |
| Medium business app | Domain-specific repositories                      |
| Large enterprise    | Repository + domain model                         |
| CQRS application    | Repository for commands, Query services for reads |
| Microservices       | Repository per service/database                   |
| Reporting system    | Separate read models                              |

## Senior interview answer

**"Do you use Repository Pattern with EF Core?"**

A strong answer:

> "EF Core already implements Repository and Unit of Work through DbSet and DbContext, so I avoid generic repositories that only duplicate CRUD operations. I introduce repositories when they represent domain concepts, aggregate boundaries, or encapsulate complex persistence logic. For read-heavy scenarios I often separate query services or use CQRS."

That answer usually demonstrates mature understanding rather than just knowing the pattern.
