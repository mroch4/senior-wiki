## What is Execution Plan?

> **An execution plan is a roadmap generated by SQL Server's Query Optimizer that shows how it will execute a query to retrieve or modify data.**

Rather than telling you **what** the query does, it shows **how** SQL Server does it.

## Why are execution plans needed?

Suppose you write:

```sql
SELECT *
FROM Employees
WHERE LastName = 'Smith';
```

There are multiple ways SQL Server could execute this query:

1. Scan the entire table.
2. Use a nonclustered index on `LastName`.
3. Use a clustered index.
4. Combine multiple indexes.
5. Perform parallel execution.

The **Query Optimizer** estimates the cost of each option and chooses the one with the lowest estimated cost.

The chosen strategy is the execution plan.

## Example

```
Employees

Id
Name
Department
Salary
```

### Without an index

```sql
SELECT *
FROM Employees
WHERE Name = 'Alice';
```

Execution plan: `Table Scan` - SQL Server reads every row.

```
Page 1
Page 2
Page 3
...
```

If there are 10 million rows, all are examined.

### With an index

```sql
CREATE INDEX IX_Name
ON Employees(Name);
```

The same query now produces `Index Seek`. Instead of scanning millions of rows:

```
Root
 |
Branch
 |
Leaf
 |
Alice
```

Only a few pages are accessed.

## Common execution plan operators

### 1. Table Scan

Reads every row in a heap.

Usually indicates:

- no suitable index
- or scanning is cheaper because most rows are needed

### 2. Clustered Index Scan

Reads every row in the clustered index.

This is **not always bad**.

If your query returns 95% of the table, scanning is often more efficient than seeking.

### 3. Index Seek

The best-case scenario for selective queries.

Example:

```sql
WHERE Id = 100
```

SQL Server jumps directly to the row.

### 4. Index Scan

Reads the entire index rather than jumping to a specific key.

Often better than a table scan because indexes are typically narrower and require fewer pages.

### 5. Key Lookup

Suppose:

```sql
SELECT Salary
FROM Employees
WHERE Name = 'Alice';
```

Index:

```sql
CREATE INDEX IX_Name
ON Employees(Name);
```

The index stores:

```
Name
Clustered Key
```

It doesn't store `Salary`.

Execution plan:

```
Index Seek
 |
Key Lookup
```

SQL Server:

1. Finds "Alice" in the nonclustered index.
2. Uses the clustered key.
3. Reads the full row from the clustered index.

Many key lookups can become expensive.

### 6. Nested Loops Join

Efficient when joining a small number of rows.

Think:

```text
For each customer

    find matching orders
```

Excellent for small result sets.

### 7. Hash Match

Used for:

- large joins
- aggregations

Builds an in-memory hash table.

Ideal for large datasets.

### 8. Sort

SQL Server sorts rows.

```sql
ORDER BY Salary
```

If there isn't an index that already provides the required order, a sort operator appears. Sorting can be expensive.

## Estimated vs Actual Execution Plan

### Estimated

Shows what SQL Server **expects** to happen.

No query execution.

Useful for quick analysis.

### Actual

Runs the query.

Shows:

- actual rows processed
- actual execution time
- actual operator costs

More useful for troubleshooting.

## Cost percentages

Example:

```
SELECT

Index Seek     2%
Nested Loop    10%
Sort           15%
Hash Match     73%
```

These percentages are **relative estimates within that plan**, not actual elapsed time. They help identify where SQL Server estimates the most work will occur.

## How to view execution plans

In SQL Server Management Studio (SSMS):

1. Open a query window.
2. Click **Include Actual Execution Plan** (or press **Ctrl+M**).
3. Execute the query.
4. Review the graphical plan shown in the **Execution Plan** tab.

You can also display an estimated plan without running the query using **Ctrl+L**.

## Reading a plan

Plans are read:

```
Right
 |
Left
```

The rightmost operator is typically where SQL Server starts retrieving data.

For example:

```
Index Seek
 |
Key Lookup
 |
Nested Loop
 |
SELECT
```

The data flows from right to left toward the final result.

# Interview Tips

- An execution plan is the **optimizer's chosen strategy** for executing a query—not the query itself.
- Learn to recognize the most common operators: **Index Seek**, **Index Scan**, **Table Scan**, **Clustered Index Scan**, **Key Lookup**, **Nested Loops**, **Hash Match**, and **Sort**.
- A **Seek** is generally preferable to a **Scan** for selective queries, but scans are not inherently bad.
- Remember that **estimated** plans use optimizer estimates, while **actual** plans include runtime information such as actual row counts, making them more valuable for diagnosing performance issues.

Is an Index Scan always bad?

> No. If a query returns a large percentage of the table, scanning can be more efficient than performing many index seeks.

Why is a Key Lookup expensive?

> Each lookup requires SQL Server to access the clustered index (or heap) to fetch columns not present in the nonclustered index. Repeating this for many rows increases I/O. A **covering index** can eliminate the lookup.

Why might SQL Server ignore an index?

> Possible reasons include:

- The query returns most of the table.
- Statistics are outdated.
- The index is not selective.
- The predicate is not **SARGable** (e.g., applying a function to the indexed column: `WHERE YEAR(OrderDate) = 2026`).
